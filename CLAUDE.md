# Rayfish

P2P mesh VPN over [iroh](https://iroh.computer). Peers are addressed by cryptographic identity (`EndpointId`), not IP. Dual-stack: stable IPv4 in `100.64.0.0/10` (FNV-1a of identity), stable IPv6 in `200::/7` (blake3, never rotates).

The crate is a library (`src/lib.rs`, daemon internals as `pub mod`) plus a thin binary (`src/main.rs`, the `ray` CLI/IPC client). The split lets benches and integration tests reach the internal data path.

The workspace also ships the mobile client: `ray-mobile` (a UniFFI cdylib wrapping the same headless daemon) and `android/` (the Kotlin/Compose app). See "Mobile" below.

> Keep this file principle-level. It documents **what holds and why**, not how every function works: the code is the source of truth for mechanics. Update it when architecture, invariants, or conventions change, not on every code edit. (The old per-module / per-flow prose lived here and drifted stale on every refactor; don't reintroduce it.)

## Build & test

```bash
cargo -q build          # --features tor (Tor transport), otel (OTLP span export)
cargo -q check --workspace --all-targets   # also: clippy, test. CI adds --locked
cargo bench             # per-packet data path (benches/forward.rs)
just cross              # x86_64 Linux;  just deploy <ip> = cross-build + install + start
just apk                # ray-mobile + UniFFI Kotlin bindings + debug APK (needs cargo-ndk, JDK 17)
just android-check      # compile the Android target in a container (no NDK needed)
```

Use `cargo -q` for all cargo commands. Keep `build` / `clippy` / `test` green at every step.

**Always pass `--workspace`.** The workspace is three crates (`rayfish`, `ray-proto`, `ray-mobile`) and a bare `cargo check` builds only the root, so a change to a shared type compiles locally and fails CI on the other two crates' own tests. `--all-targets` matters for the same reason: a struct literal in a `#[cfg(test)]` block is where a new field first breaks.

## Run

The daemon (`ray daemon`) owns the TUN device + iroh endpoint and runs as a system service; the CLI talks to it over Unix-socket IPC. Full command surface + flags: `ray --help`, `ray <cmd> --help`.

Service management never calls `systemctl` directly: `init_system::InitSystem` detects systemd / OpenRC / SysV init and owns the per-init unit template (`contrib/rayfish.{service,openrc,init}`), install path, and start/stop/enable commands. macOS (launchd) is a `#[cfg]` branch at the call sites.

```bash
sudo ray up | down            # activate / standby (down keeps peer connections, drops only the data plane)
sudo ray start | stop | restart | install | uninstall | set-operator
ray create | join | leave | nuke | kick | ephemeral | hostname | status
ray invite | requests [accept|deny] | admin          # admission + coordinators
ray connect [list|approve] | contact | pair | unpair  # direct links + multi-device identity
ray firewall … | apply | alias | identityof          # policy
ray exit-node allow | disallow | use | none | status  # internet gateway (offer: Linux/macOS/BSD, use: Linux/macOS)
ray send | files | config | gui | mdns | update | ping | netcheck | logs | report
ray completions [shell] [--install]                  # tab completion (installed by `ray up`)
```

**Privilege (Tailscale operator model):** the always-root daemon does privileged work; clients are unprivileged. The IPC socket is `0666`; authority is a per-request `SO_PEERCRED` UID check (`Daemon::check_authorized`), not socket permissions. Reads are open to any local user; mutations need root or the configured `operator_uid`. Only service management (`install`/`start`/`stop`/`restart`/`uninstall`/`set-operator`/`daemon`) needs `sudo`; `up`/`down` and everything else is IPC. `ray up`/`install` auto-grant operator to `$SUDO_USER`.

## Architecture

```
App -> TUN (100.64.x.x / 200::x) -> rayfish -> iroh QUIC datagrams -> peer
```

One iroh endpoint + one TUN, shared across all networks. There is **one mesh connection per peer device** (not one per network): it carries traffic for every network the two peers share, under a single node-wide ALPN `rayfish/mesh/<version>`. The network is selected **in-band**: control frames carry `ControlFrame.net`, data datagrams carry a 2-byte network-handle tag. The `<version>` segment is the mesh protocol-version gate: peers on different versions share no ALPN and cannot connect.

The daemon (`src/daemon/`) is an **acyclic graph of `Arc` services** rooted at **`Daemon`** (the composition root: data plane, IPC dispatcher, service handles). Services own their own state and are reached by an `Arc`, so leaf tasks call them directly rather than signalling up a channel:

- **`Transport`**: endpoint, identity, blob store, metrics (the foundation everything depends on).
- **`NetworkRegistry`**: the networks map + all membership / coordinator / admission / reconverge logic (as `impl NetworkRegistry` blocks across `mesh/*.rs`).
- **`ConnectionManager`**: one QUIC connection + one id-keyed reader per peer, the frame demux, `tun_tx`.
- **`DnsService`** / **`FileService`** (`FILES_ALPN`/`PAIR_ALPN`) / **`ConnectService`** (`CONNECT_ALPN`).

## Mobile

Android runs the same core, not a reimplementation. `ray-mobile` is a UniFFI cdylib exposing a `Node` that wraps a headless `DaemonState` (`build_headless`), so create/join/pair/status/firewall all go through the desktop code path. There is no daemon process and no IPC socket on Android: Kotlin calls the `Node` directly.

- **Platform specifics stay in `ray-mobile`.** The TUN fd comes from Android's `VpnService` and is handled in `android_tun.rs`; `RustlsInit.nativeInit(context)` must run once after `System.loadLibrary` to hand the `JavaVM` + app `Context` to `ndk-context` (system DNS) and `rustls-platform-verifier` (trust store). Everything else is a thin map from the core's `IpcMessage` results to UniFFI records.
- **Same control/data plane split.** `Node::start` brings up the control plane; `Node::up` / `Node::down` attach and detach the forward loop over the VpnService fd, leaving peer connections up.
- **Bindings are generated, not written.** `android/app/src/main/java/uniffi/ray_mobile/ray_mobile.kt` is regenerated by `just apk`; never hand-edit it. Changing the UniFFI surface means regenerating and fixing the Kotlin callers in the same change. CI regenerates them too and fails on any diff, so a stale committed copy is a red build rather than something the next APK build quietly fixes.
- **UI is Compose**, one screen per tab (`HomeScreen`, `NetworksScreen`, `NetworkDetailScreen`, `YouScreen`) with shared widgets in `ui/components/Components.kt` and QR scan/render in `ui/qr/`.

## Design invariants

The rules the code upholds. Read the code for the mechanics.

- **Reachability = a shared network.** Two peers exchange packets iff they share ≥1 network (a QUIC connection only exists within one; the receiver also drops any datagram whose handle-tagged network its verified roster no longer shares with the sender). The network split is coarse access; the per-device firewall is the fine layer.
- **Room id ≠ admission, but it is a read capability.** The network public key is a discovery key, never a credential. Open networks auto-admit; closed networks gate on a one-time invite, a reusable key (carried in the signed blob), or live approval (`ray requests <net> accept`). It still buys a read, though, and the docs have to say so: the pkarr record it addresses names the group blob hash, and the blob store serves any hash to any dialer, so anyone holding the id can fetch the whole roster (identities, mesh IPs, hostnames, user identities, device certs). That is what makes a leaked invite a roster disclosure and not just a spent credential.
- **Naming a network is not being in it.** A control frame is routed to a per-network handler by the `net` in its envelope, and that is a public key anyone can name, so the sender is checked against that network's roster before dispatch (`AcceptHandler::knows_sender`), the control-plane counterpart of `resolve_inbound_by_id` on the data plane. Three messages are exempt because each is how a peer legitimately not on the roster yet reaches us: `JoinRequest`, `MeshHello`, and `SignedRecord` (self-verifying against the network key, and the thing that repairs a roster too stale to recognize its own coordinator, so gating it on that roster would be circular; what stops a replay there is a per-network timestamp floor, not the wall). Per-arm authority checks stay on top of this, not instead of it: the wall answers "may this peer speak here at all", `sender_is_coordinator` answers "may it say *this*".
- **A device cert is verified wherever it is read, not only where it is doubted.** The cert binds a device key to a user identity, and `device_user_map` turns that binding into what the inbound firewall, mesh SSH, own-device file auto-accept and leave-pruning authorize on. So it is verified (signature, and that it names the key that actually dialed) on every path that records it, including the one where the sender claims no identity but its own: an unchecked cert there is still a `user_identity` taken on the sender's word. `ray unpair` cannot invalidate a signature, so the blob's nullifier set is applied at the same point.
- **The signed `GroupBlob` is the source of truth.** One pkarr record per network, signed by the per-network key (the pkarr address *is* the public key, so records are MITM-resistant). Roster, suggested firewall, reusable keys, and `nullifiers` (`ray unpair`) all ride it. Members reconverge from the signed record on the group poll or a payload-free `MemberSync`/`BlobUpdated` **trigger**: control messages are triggers, never trusted data.
- **Coordinator = network-key holder.** Any holder can admit, suggest firewall, kick, and republish; `ray admin add` grants the key (co-coordinator). Admission survives any single coordinator being offline (the joiner dials the full coordinator set).
- **Firewall is secure-by-default.** Inbound TCP/UDP denied, inbound ICMP allowed (a seeded, removable rule), outbound allowed; a stateful conntrack lets return traffic back. Coordinator suggestions are advisory and consented per-node; local rules are never touched by reconverge.
- **Hostname authority = invite binding.** An invite-bound hostname is assigned exactly and a colliding claim is rejected; a free hostname gets suffix collision resolution. The roster is the single source of truth for `*.ray` DNS.
- **Data plane vs control plane.** The daemon connects every saved network at startup and keeps those connections for its lifetime (dropped only on leave/nuke/shutdown). `up`/`down` (`activate`/`deactivate`) toggle only the data plane (TUN link, routes, Magic DNS, forward gate); `start`/`stop` toggle the whole process.
- **IPv6-only is a start-time mode.** For sharing a host with a VPN that owns `100.64.0.0/10`; read once at startup because the TUN's addressing is fixed when the device is created. The derived IPv4 is still assigned, as a `/32` (only the connected route collides), because it stays the node's internal handle for peer table, roster and status. Magic DNS moves to `MAGIC_DNS_V6` (`200::53`). The v4 magic IP there is not redundant but broken: Tailscale drops `100.64.0.0/10` traffic not arriving on `tailscale0`, and our reply is synthesized *from* that IP *into* the TUN, so netfilter eats it. Routing is not the only thing that can stop a packet. Desktop reads `settings.toml`; embedders pass it in (`build_headless_with_setting`) because Android's config dir is app-private. Changing it means a new daemon and a new tunnel with it.
- **The IPv6-only setting is three-valued, and so is the mode it resolves to.** `Ipv6Only::{Auto, On, Off}` (`ray-proto`) is the stored setting and what `ray status` reports. `auto` lets the startup scan decide (something else on `100.64.0.0/10` means start IPv6-only, so the node runs rather than refusing); `off` is the standing refusal, which is why it cannot be a bool. An auto decision is **never written back**, so it travels through `Overrides`, not the config, and the data path asks `Ipv6Only::enabled()`. `decide_ipv6_only` holds the table; `resolve_ipv6_only` applies it and is the only path that scans, so tests never do. The scan skips our own mesh IPv4, or rebuilding over a live `VpnService` would latch the mode on for good.
- **Two separate facts drive DNS answers, and both are needed.** *This node* cannot use mesh v4 (a flag on `Resolver`, so even a dual-stack peer is not offered an A record here), and *that peer* cannot (`Member.ipv6_only` on the signed roster, carried into `HostnameEntry`'s `Option<Ipv4Addr>`). Withheld A records are NODATA, never NXDOMAIN, which would fail the AAAA alongside them.
- **The daemon resolves its own names, and never through itself.** The endpoint gets an explicit `DnsResolver` (`transport::control_plane_nameservers`): configured `dns_upstreams`, then the host's resolvers as read before any takeover, then a public server. iroh's default reads `/etc/resolv.conf` at bind, which is both a circle (the file may already name our magic IP) and a single point of failure (#111: one dead nameserver took the control plane down, relay and pkarr included). The overlay filter is what keeps the magic IP out of the list. `None` from `system_nameservers` means *unreadable here* (Android keeps them behind JNI), not *none*, so that host keeps iroh's reader rather than have its Private DNS stepped over.
- **`/etc/resolv.conf` is shared, not owned.** With another overlay's resolver in the file (`foreign_mesh_resolver`: a `100.64.0.0/10` nameserver that is not ours), both daemons re-assert and the contents are whichever write landed last. That is only fatal while each write *replaces* the other, so ours does not: ours goes first (glibc stops at the first server that answers, so second place is no place), theirs stays as the next nameserver and receives everything outside `.ray`, and `MERGE_COOLDOWN` damps the race rather than trying to win it. An additive write needs a subtractive undo, so every path that removes us strips our own lines instead of restoring a backup that predates the merge. A nameserver change exits the watcher with a `Recapture` and re-runs detection, since our upstreams were captured from that file (#111). Sharing is refused outright unless our resolver address is the v6 one, since a v4 magic address sits in the range that VPN filters and would make us an unanswering first nameserver, which costs every lookup on the host a resolver timeout. **On a shared file we stop forwarding entirely** (`set_defer_off_mesh`): every captured server is rendered after ours, and a name outside `.ray` is answered REFUSED, which glibc treats as a failed server and takes to the next `nameserver` line at once (silence would cost it `timeout:5` instead). That is not a shortcut. Relaying the host's general DNS puts a userspace hop in front of every name, flattens whatever the other resolver does natively, and is the only reason two resolvers pointed at each other can loop, which they can: Tailscale drops only its *own* service IPs from what it reads (tailscale/tailscale#7816). `.ray` stays ours to answer, misses included.
- **A shared resolver's death is invisible in the file, so it is probed.** Neither daemon overwrites a file it does not own (their `Close`, our `restore_file`), so a VPN that leaves while we hold the file leaves its address sitting in it, no longer answering, with nothing for the watcher to read. On a host that declines off-mesh names that address *is* the rest of the machine's DNS, so the re-assert tick probes it and `SharedResolverGone` stands all the way down (`revert`, un-quiet NM) rather than rebuilding. Nothing else can: the servers it replaced are gone (they drop their backup on the way out, ours is a copy of their file), so the only way back is letting the host regenerate the file from DHCP and taking it over again on the retry.
- **Search domains go wherever DNS actually lives.** They are what makes a bare `box` resolve, and the manager path only speaks resolved, so on the hosts that fall past resolved to a file-owning backend they went nowhere. They are a `DnsConfigurator` method: split-DNS backends hand them to the manager, file-owning backends write them into the file. The registry announces them before the data plane exists, so `DnsService` caches the list and re-installs it into whatever backend it adopts next. A captured `search` line is filtered of our own domains, or a restart over our own file would readopt them as the host's and outlive the `ray leave` that dropped them.
- **The outbound network tag comes from what the peer acknowledges.** A datagram is stamped with a network handle and the receiver drops it unless it shares that network (`resolve_inbound_by_id`), so the sender's pick must agree with the receiver's view or the peer is black-holed. Our shared set is not that view: a peer that left a network without being able to say so stays in our roster for good when we hold the network. `PeerEntry::route` therefore picks from the handles the peer announced (`in_handles`), falling back to the plain pick only before that lands. Names keep resolving from the stale roster either way, which is why the failure reads as "the mesh is up and the connection times out".
- **Reachable is not connected, so a trigger dials.** An on-demand peer idle-closes its mesh links while its endpoint stays up, so it is dialable the whole time the peer table shows it absent. `broadcast_member_sync` therefore delivers over live connections *and* dials the roster members it missed, or a phone would learn of a kick or a firewall suggestion only at its next group poll (`GROUP_POLL_INTERVAL_BATTERY`, 15min on Android vs 60s elsewhere). The dial skips peers whose last attempt failed inside `ABSENT_DIAL_COOLDOWN`. The poll stays as the backstop for what no trigger covers (every coordinator offline while the blob changed). **The long poll is keyed on the platform, not on `on_demand`:** that is a desktop config key a wired node may set for its own reasons.
- **A full tunnel takes only the families *both ends* carry** (`ExitFamilies::tunnelled`: our own data plane, intersected with the gateway's claim). IPv6-only mode tunnels IPv6 and leaves the host's IPv4 egress with whoever owns `100.64.0.0/10`. That is the mode's own premise, not a workaround: mesh IPv4 carries no traffic, so claiming the host's IPv4 default would source transit from a `/32` this mode deliberately leaves unrouted. It also keeps `is_disabled_mesh_ipv4` out of it, since exit return traffic is then IPv6. The gateway half of the intersection is the same argument from the other side: a family it cannot return is a black hole, so it is left direct rather than tunnelled, and only a gateway that can return *nothing* is refused. Narrowing beats refusing because refusing takes the family that works out of the tunnel too. **Install is per-family and also tears down the family it stopped claiming; teardown is never per-family** (`tunnel_families`), because kernel rules outlive the process and the panic hook `abort()`s, so neither end may assume the other ran. The gateway side was always dual-stack and is untouched. Two things follow: the offer carries `Member.exit_families`, and a partial tunnel is stated rather than left to a leak test (`ray exit-node use` warns, `ray exit-node status` says `IPv6 only` / `IPv4 only`; an *absent* claim narrows nothing, see the wire convention below); and a tunnel that carries IPv6 and not IPv4 points the forwarder at an IPv6 resolver for its lifetime (`exit_node::tunnel_upstreams`), since every captured upstream is IPv4 and would leave *around* the exit. That override does not overrule an explicit `dns_upstreams --replace` holding only IPv4 servers: `replace` names an internal resolver whose names nothing else answers, IPv4 egress is reachable in this mode anyway, and a query sent around the exit is recoverable where a wrong answer is not.
- **`exit_families` is a claim about the *return* path, not just the uplink.** A gateway in IPv6-only mode has an IPv6 uplink and still cannot carry a client's IPv4: it assigns mesh IPv4 as a `/32` with no `100.64.0.0/10` route, so the forward direction masquerades out fine and the un-NATted reply finds no way back into its TUN. So the claim is derived from both facts (`ExitFamilies::from_uplink`), giving `V6` where the uplink alone would have said `Dual`. A false positive claim is worse than the `Unknown` the three-valued type exists to express, because what the client does with it is narrow its tunnel: a claim of `V4` from a gateway that cannot in fact return IPv4 leaves that family tunnelled into a hole, while `Unknown` narrows nothing. The *warning* stays asymmetric on purpose: an unclaimed gateway is a guess in both modes, but for a dual-stack client the thing it is guessing about is a gateway running IPv6-only mode itself, which is rare, while every network with a coordinator predating the field has unclaimed gateways, so warning there would fire constantly and say nothing.
- **That IPv6 gate is a standing property, not a selection-time one, which is why the refusal is split in two.** "Does not advertise an exit node" flickers (a coordinator rebuild, a gateway mid-restart), and dropping a live tunnel on it would leak the traffic the user chose to tunnel, so it is checked only when the user picks. "Cannot carry IPv6" is re-checked on every re-apply (`ipv6_gateway_refusal` in `reload_exit_state`), because while it holds the tunnel carries nothing at all and nobody has to touch the selection for it to become true: `ipv6_only = auto` turns the mode on by itself the first time something else claims `100.64.0.0/10`. There the safe side is *not* installing, the opposite of the no-silent-fallback rule beside it. The advertised flag is re-probed on the reconverge that publishes it for the same reason, or a gateway that gained IPv6 would keep saying otherwise until someone restarted its data plane. Because that refusal can arrive with nobody touching the selection, the config and the installed tunnel are allowed to disagree, and `ray exit-node status` has to say so: it reports the selection as `NOT in effect` with the reason (`exit_selection_problem`), since a bare `using: <peer>` over direct egress is exactly the state a user who chose to tunnel would not think to check.
- **Pointing our forwarder at an IPv6 resolver is not the same as an application's lookups following the tunnel.** Which queries reach the daemon at all is the OS DNS backend's decision, and the override only governs what we forward ourselves. The split-DNS backends (systemd-resolved, NetworkManager, resolvconf) register `~ray` as the sole routing domain, and a shared `resolv.conf` declines off-mesh names outright, so on either the rest of the host's lookups go to its other servers over the IPv4 this mode does not tunnel, and leave around the exit. macOS avoids it by re-asserting a catch-all match domain while the tunnel is up (`DnsService::reassert_os_config`); Linux has no equivalent yet and the daemon warns instead. Don't restate the macOS behaviour as if it were the general case.
- **Our policy rules outrank a peer VPN's, so we mirror what they would have matched.** `PREF_TUNNEL` is a catch-all far above the preferences a co-resident VPN uses (Tailscale's are 5210-5270), and `PREF_MAIN`'s `suppress_prefixlength 0` only rescues routes in `main`, while a policy-routing VPN keeps its prefixes in a private table. So the client install copies every foreign table's non-default routes into `EXIT_TABLE` first (`mirror_foreign_routes`), where longest-prefix hands those destinations back to the interface that owned them. **The copy is only half of it:** `PREF_SRC` and `PREF_BYPASS` sit above the catch-all and both look up `main`, so traffic sourced from that VPN's own address (an inbound session's replies) or carrying our conntrack mark would still miss and take main's default. `PREF_FOREIGN` (98) sends those destinations to our table too, in a single rule: `suppress_prefixlength 0` makes the lookup its own selector, matching every mirrored prefix and suppressing our default, the same trick `PREF_MAIN` plays on `main`. So the rule reads the routes instead of naming them, and it can neither outlive one that failed to install nor grow with the co-resident VPN's route count. One-directional by construction: we only ever write our own table, and the teardown flush drops the copies with the default. macOS needs none of this, its split default living in the one table a foreign route is already more specific than.
- **A tab never starts the daemon and never blocks the shell.** Completion is dynamic (the installed script is a stub that calls the binary), so it runs on a keystroke: it answers from an open IPC read within a 300ms budget, and every failure — no socket, no daemon, no reply in time — is the same answer, no candidates. `ray up` installs the stubs system-wide because that is where shells find them without an rc edit.

## Conventions

- **Writing:** plain and direct.
- **Rust:** the crate's `AsyncMutex` alias lives in `src/lib.rs`, so `Mutex` in this codebase always means the std one. **Never** share an I/O resource (TUN, socket, stream) behind a `Mutex`: split read/write halves. Avoid `Mutex` generally: prefer channels, atomics, or `RwLock`/`ArcSwap` for fast non-async state.
- **Wire protocols are ALPN-versioned** (`rayfish/{mesh,files,pair,connect}/<v>`). ALPN negotiation is the *only* compatibility gate (no in-band version handshake), so when you change a wire protocol incompatibly, bump its version in the same change. Wire format = 4-byte BE length + msgpack; TUN MTU 1280.
- **Adding a field to the wire is a version bump, and reordering two is a silent corruption.** The control wire is msgpack **array**-encoded (`rmp_serde::to_vec`), so a struct's declaration order *is* the wire format and its field count is part of it. Fields are still only ever appended, with `#[serde(default)]`, but that buys one direction and not the other: a new build reads an older peer's shorter array and defaults the tail, while an older build reads the longer array and rejects the value whole. Both ends of a connection share one ALPN, so there is no additive lane left: a field addition, a removal, a type change, and **reordering two fields** all need a version bump in the same change. Reordering is the dangerous one: between differently-typed fields it errors loudly, but between two `bool`s it decodes clean and silently swapped, and a diff that only moves a line does not look like a protocol change. Three tests in `membership.rs` pin this: the shorter array defaulting, the longer one failing, and the silent swap.
- **What is array-encoded and what is not.** Compact applies to what crosses a network: control frames, the pair/connect/files protocols, and `canonical_group_bytes` (content-addressed, so a re-encode is just a new hash). It bought about a third off a roster blob, which is the largest thing on the wire; the per-packet path never touches this codec at all (raw datagrams, 2-byte handle tag). Two callers deliberately stay on `to_vec_named` and must not be "made consistent": `identity::store_device_cert` writes to disk, where no ALPN gate exists and a re-encode would strand every already-paired device's identity binding; and IPC (`ray-proto/src/ipc.rs`), which has no version negotiation and is read by a CLI whose binary is swapped before the daemon restarts. Neither saves a network byte, and `skip_serializing_if` is still safe (and still used) in those two.
- **The roster blob is compact but *not* ALPN-gated, so nothing keeps an old peer away from it.** Everything else compact rides an ALPN we version; the blob rides `iroh_blobs::protocol::ALPN`, which is shared and not ours to bump, and only the *join* path checks `mesh_version_from_record`. A group poll does not, so an old build still fetches the bytes and tries to decode them. It cannot, and appending does not save it: the tolerance above runs one way, and what an old build reads is a *longer* array than its struct has slots, which rmp-serde rejects whole (`an_older_build_cannot_read_an_appended_field`). So a `Member` field is not the free additive change it was under keyed encoding. Bump the mesh version in the same change and let the ALPN split the network where it can be seen, rather than leaving old peers connected and quietly stuck on the last roster they could parse. The bridge does run the other way, which is what makes an upgrade survivable at all: rmp-serde reads a struct from a map or an array, so a node that upgrades ahead of its coordinator still converges from the old named blob (`a_named_encoded_blob_from_an_older_build_still_decodes`). It then re-encodes it compactly in `refresh_snapshot`, so its local hash never equals the one the record commits to. That is why convergence is tracked as `converged_hash`, the hash we accepted, and not as the snapshot's: the snapshot is what we would *publish*, and comparing the record against it reads a re-encode as a change forever, refetching every poll and never reaching the converged branch that syncs exit offers and drains a pending rename.
- **A wire struct may not carry `skip_serializing_if`.** In an array there is no key to omit, so a skipped field is a missing *slot* and every field after it shifts one place left. Between differently-typed fields that errors; between two of the same type it decodes clean and wrong. `HostSuggestions` (`ray-proto/src/policy.rs`) is the reason this is a rule and not a note: `allows` and `denies` are both `BTreeMap<String, String>`, it rides the signed blob, and skipping an empty `allows` turned every coordinator `deny` into an `allow` on every member. `a_deny_only_suggestion_does_not_decode_as_an_allow` pins it. The attribute stays legal only on the two named-encoded carve-outs above.

- **Config** lives under `config::config_dir()` (`/etc/rayfish` on Linux, `~/Library/Application Support/rayfish` on macOS, i.e. the *daemon's* home; `RAYFISH_CONFIG_DIR` overrides it everywhere, and daemon + CLI must both see the same value). Sharded and atomic: globals in `settings.toml`, one network per `networks/<name>.toml`; secret-bearing files are `0600 root:root` and writes go through `config::write_file`. Single-value settings are never bespoke IPC: each is a typed key, one enum per store (`GlobalKey`/`FirewallKey`/`NetworkKey` in `ray-proto/src/settings.rs`), carried by `ConfigSet`/`ConfigGet` or their `Net` twins, with behavior in `src/config/settings.rs`. The per-store split is load-bearing: every `apply_*`/`render_*` matches its enum exhaustively, so a new key cannot compile until each handler serving it grows an arm. Adding a setting means an enum variant, its `apply`/`render` arms, and a CLI arm, never a new message type.
- **IPC is one request, one response, with one exception.** `ray logs` answers with a run of `LogChunk` frames, ended by an `Ok` sentinel or (under `--follow`) not at all: a day of `rayfish=debug` output is many times the 1 MiB frame cap, and a follow has no last frame by definition. It is the only handler that writes to the stream, which is why `handle_ipc_client` dispatches it ahead of `handle_request`. A second streaming reply is a reason to factor the pattern out, not to widen every handler's signature.
- **CLI help is grouped in `src/cli/help.rs`, per page.** clap has no subcommand grouping (`help_heading`/`hide_short_help` are argument-only), so a grouped `-h` list is rendered there from the clap model and the help template drops `{subcommands}`. `PAGES` maps a command path to its groups (`&[]` = the root, `&["firewall"]` = `ray firewall`); a new command must join the groups of the page it sits on or it appears nowhere, and the tests enforce both directions per page. Group a page only when it outgrows a flat list: below about eight actions a heading per two entries is noise. **`about` is one line inside 80 columns at every depth** (`every_about_fits_the_listing` walks the whole model), with the rest after a blank line, where it becomes `ray help <command> <action>`; `wrap_help` is on so those paragraphs wrap to the terminal. Subcommands stay *visible* in the clap model unless hiding them is the point: `hide = true` suppresses clap's list but `clap_complete` also skips hidden subcommands, which silently guts tab completion for a command meant to be typed — and is exactly right for one that isn't (`open`), or for an old spelling kept alive only so existing scripts keep working (`accept`, `deny`, `connections`, `auto-update`).
- **`--json` is per-command, never on the root.** It is declared on each command that renders JSON, `global = true` so it also parses after that command's action (`ray firewall show --json`). Declaring it on `Cli` would put it back on all 44 commands, most of which would ignore it in silence.
- **Logging** is `tracing`: console at `info`, rolling daily files at `rayfish=debug` (bundled by `ray report`). The daemon panic hook restores DNS then `abort()`s so the service manager restarts it (fail-fast, never limp).
- **Git:** conventional commit subjects (`feat`/`fix`/`docs`/…) so git-cliff can generate the changelog.
- **CHANGELOG:** add a user-facing `[Unreleased]` entry (`Added`/`Changed`/`Fixed`/`Security`/`Performance`, in Keep a Changelog's order, so `Security` comes after `Fixed`), describing behavior from the user's view, for any user-visible change; skip pure-internal churn (refactors, CI, chores).
